Upgrade Decision: CONDITIONAL APPROVAL

The cluster is a healthy IBM IKS managed environment on v1.36.5 with 6 worker nodes across 3 zones. No deprecated or removed Kubernetes APIs are actively in use, PodSecurityPolicy was already removed, no admission webhooks are registered, and resource utilisation is extremely low (CPU <1%, Memory <11%).

The upgrade is viable but conditionally blocked by two critical pre-conditions: (1) A Prometheus admission-create Job has been stuck in ImagePullBackOff for 23 days due to ghcr.io being unreachable. (2) IKS v1.37 platform availability has not been confirmed.

Resolve both critical issues before initiating the upgrade.

🚨 Critical Issues — Must Resolve Before Upgrade
CRITICAL 1 Prometheus Admission-Create Job — 23-day ImagePullBackOff
What Will Break:Job prometheus-stack-kube-prom-admission-create in monitoring ns has been stuck for 23 days. Image ghcr.io/jkroepke/kube-webhook-certgen:1.8.8 cannot be pulled (ghcr.io connection timeout: 140.82.112.34:443). This job provisions TLS certificates for Prometheus-operator admission webhooks.
When It Will Break:Already broken. Pre-existing condition. Will persist and block clean post-upgrade state.
Impact:Incomplete monitoring stack. Risk of missing webhook certs if Prometheus-operator later registers webhooks after upgrade.
Severity:Critical — Blocking
Remediation:Step 1: kubectl delete job prometheus-stack-kube-prom-admission-create -n monitoring. Step 2: Either allow ghcr.io access or mirror image to ICR. Step 3: Redeploy kube-prometheus-stack or remove it entirely if not needed.
CRITICAL 2 IKS v1.37 Platform Availability Not Confirmed
What Will Break:IBM IKS manages Kubernetes version availability on its own cadence. K8s 1.37 may not yet be published on IKS. Attempting upgrade to an unavailable version will fail at initiation.
When It Will Break:At upgrade initiation via ibmcloud CLI.
Impact:Upgrade fails; cluster stays on v1.36. No degradation, but wasted effort.
Severity:Critical — Blocking
Remediation:Run ibmcloud ks versions to confirm 1.37 is listed. Review IBM Cloud changelog for IKS 1.37 GA date. Wait if not yet available.
🔶 High Risks
HIGH 1 IBM-Managed Component Compatibility Unverified
Components:Calico v3.31.7 + Tigera Operator v1.40.15 · IBM IKS NGINX ALB 1.15.10 · IBM VPC Block CSI v5.1.64
Risk:These are IBM-managed add-ons. IBM typically upgrades them in lock-step with the cluster upgrade, but the specific IKS v1.37 compatibility matrix has not been verified. Upstream Calico 3.31 supports K8s up to 1.32; IBM ships validated custom builds. ALB 1.15.10 (ingress-nginx based) may have version constraints.
Impact:Potential networking outage, storage inaccessibility, or ingress failure if add-ons lag behind during upgrade.
Remediation:Run ibmcloud ks addon versions. Review IKS 1.37 release notes at cloud.ibm.com/docs/containers. Confirm IBM auto-update policy for managed add-ons.
HIGH 2 Prometheus-Operator CRDs Without Running Controller
Components:10 monitoring.coreos.com CRDs installed (alertmanagerconfigs, prometheuses, servicemonitors, etc.) — but no Prometheus/AlertManager/ServiceMonitor objects exist and no operator pod is running.
The monitoring stack is in a partially-deployed, inconsistent state. CRDs are installed but ownerless.
Impact:Post-upgrade CRD schema changes could cause reconciliation failures if the operator is deployed later. Orphaned CRDs are a maintenance liability.
Remediation:Either fully deploy kube-prometheus-stack (fix image issue first) or run helm uninstall prometheus-stack -n monitoring to cleanly remove all CRDs and resources.
HIGH 3 kubectl Client Version Skew — 5 Minor Versions Behind
Client:kubectl v1.31.1 — Server: v1.36.5+IKS — Skew: 5 minor versions (supported: ±1)
kubectl explicitly warns about this skew. Post-upgrade to 1.37 the skew grows to 6 minor versions. API requests using v1.37-specific features or changed schemas may fail silently or return errors.
Remediation:Upgrade kubectl to v1.37.x before upgrade: curl -LO https://dl.k8s.io/release/v1.37.0/bin/$(uname -s | tr A-Z a-z)/amd64/kubectl
HIGH 4 Worker Nodes Behind API Server Patch Level
API Server:v1.36.5+IKS — Worker Nodes: v1.36.3+IKS (all 6 nodes)
Nodes have not been refreshed to the latest worker image. IBM IKS worker upgrades are a separate operation from master upgrades. Starting a major minor upgrade from a stale patch baseline increases risk.
Remediation:Run ibmcloud ks worker update --cluster <CLUSTER_ID> --worker all to bring nodes to v1.36.5 before upgrading master to v1.37.

✅ Required Actions & Recommended Upgrade Order

— Pre-Upgrade (Critical, Blocking) —

  1. Confirm IKS v1.37 availability — Run ibmcloud ks versions. Only proceed if 1.37 appears. Review IBM Cloud changelog for IKS 1.37 GA date at cloud.ibm.com/docs/containers.
  2. Resolve Prometheus stuck job — kubectl delete job prometheus-stack-kube-prom-admission-create -n monitoring. Then either restore ghcr.io access, mirror ghcr.io/jkroepke/kube-webhook-certgen:1.8.8 to ICR, or remove kube-prometheus-stack entirely: helm uninstall prometheus-stack -n monitoring.
  3. Update kubectl to v1.37.x — Eliminate the 5-minor-version client skew before upgrade.
  4. Bring nodes to v1.36.5 — ibmcloud ks worker update --cluster <CLUSTER_ID> --worker all.
  5. Verify IBM add-on compatibility — ibmcloud ks addon versions. Confirm Calico, ALB, VPC CSI compatibility with IKS v1.37 in IBM documentation.

— Recommended Upgrade Order —

  1. Pre-flight validation — Confirm all blocking issues resolved, all 6 nodes Ready, stuck job deleted.
  2. Refresh worker nodes to v1.36.5 — Ensure clean baseline patch level before minor version bump.
  3. Upgrade control plane — ibmcloud ks cluster master update --cluster <CLUSTER_ID> --version 1.37. IBM manages HA rollover.
  4. Monitor IBM auto-upgrades — Calico, CoreDNS, Konnectivity, metrics-server, snapshot-controller auto-update. Watch pod restarts: kubectl get pods -A -w.
  5. Upgrade worker nodes to v1.37 — ibmcloud ks worker update --cluster <CLUSTER_ID> --worker all. Nodes drain and reboot one at a time per zone.
  6. Verify ALB and VPC CSI post-upgrade — Confirm pods running on new versions, ingress health endpoint returns 200.
  7. Run post-upgrade validations — Full checklist below.

— Post-Upgrade Validations —

  • ☐ All 6 nodes Ready: kubectl get nodes
  • ☐ calico-node DaemonSet fully running: kubectl get pods -n calico-system
  • ☐ CoreDNS, NodeLocalDNS pods healthy in kube-system
  • ☐ ALB pods running on updated image
  • ☐ VPC Block CSI controller and node pods healthy
  • ☐ Ingress health returns 200: check k8s-alb-health ingress
  • ☐ Metrics server responds: kubectl top nodes
  • ☐ API server healthy: kubectl get --raw /healthz → ok
  • ☐ No new Warning events: kubectl get events -A --field-selector type=Warning
  • ☐ Deploy test workload and verify PVC provisioning in non-production namespace
